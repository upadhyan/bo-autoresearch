# Issue #21: Spec: BO Autoresearch plugin v1

- State: OPEN
- Author: upadhyan
- Created: 2026-09-28T22:54:52Z
- Labels: ready-for-agent


## Problem Statement

A researcher points an agent at a codebase and says "make this objective better". Today's agent-driven autoresearch loops fail that researcher in predictable ways:

- **They are myopic.** An agent tries one change, sees no gain, and discards it, without ever asking whether it would help together with something else.
- **They evaluate without structure.** One noisy run is taken as evidence, and there's no pre-registered notion of what would count as failure.
- **They spend agent tokens doing a search BO would do better.**
- **They interpret their own results after the fact.** This lets them rationalise, quietly move goalposts, or "improve" the score by editing the evaluation.
- **They lose track of time and duties.** They stop early, forget to re-check things, and can't be trusted to keep a budget or respect "don't touch that" instructions.

The researcher ends up with an unreproducible pile of edits and no clear record of what was tested, what worked and why.

## Solution

**BO Autoresearch** is a Claude Code plugin. An orchestrating agent proposes **falsifiable hypotheses**, each exposing one or more **levers**, and Optuna Bayesian optimisation searches those levers within each **round**. Everything that must be trustworthy is deterministic and lives in a small bundled Python harness, `boautoresearch`:
- statistics, verdicts and seeds;
- the budget and stopping;
- enforcement.

The LLM makes the judgement calls: what to try, how to code it, whether it fits the user's intent, and what might interact. Harness refusals and hooks force each of those calls to happen.

From the user's side:

1. **Pre-loop grilling.** `/boautoresearch:start` interviews the user about the objective, the research brief, directives, protected paths, fidelity and budget. It runs a **calibration round** to measure noise, lets the user set the **minimum meaningful effect**, shows the generated hypothesis list once, then goes autonomous.
2. **The research loop.** It runs round after round, never stopping on a stall. It ends only when the budget is spent, the user stops it, a target is confirmed, or the hypothesis list is **exhausted**. A short `SUMMARY.md` always says what's been tested, what's working and what isn't.
3. **The hand-back.** The user gets a verified **distilled branch** (a clean re-implementation of only what worked), the configurable research branch, a `REPORT.md`, and CSVs of every trial and hypothesis. Nothing is ever merged into the user's branches.

## Implementation Decisions

Terms follow the project glossary (`CONTEXT.md`). Every decision below came out of a closed ticket under the map [Map: BO-driven autoresearch plugin](https://github.com/upadhyan/bo-autoresearch/issues/1), and the resolution comments there hold the full reasoning. Where a later ticket amended an earlier one, the amended form is stated here.

### Modules
- **Plugin shell.** A Claude Code plugin with a manifest, one orchestrator skill (`/boautoresearch:start`, which runs pre-loop grilling and then the loop), five subagent definitions, a `hooks.json`, and the bundled `boautoresearch` package source.
- **`boautoresearch` harness.** One deep module with two interfaces:
  - the **runner-side** interface, imported by lever code and runner scripts;
  - the **agent-side** JSON CLI.

  Behind them sit the experiment log and its state tables, eligibility and warm start, the verdict engine, the round scheduler, the budget ledger, code and environment management, the enforcement checks, and summary and report generation. It is installed into each run's venv from the plugin's own directory, not from PyPI.
- **Hook adapters.** Standard-library Python scripts that call `boautoresearch check …` and hold no logic of their own.
- **Dogfood benchmark.** A toy project, run config, fixtures, expected verdicts and a checker (see Testing Decisions).

### Runner-side interface
Six names are the whole surface. This shape is taken from the throwaway prototype on the `prototype/harness-api` branch:
```python
lever(name)          # effective value (masking applied); ONLY way to read config.
                     # Outside the harness: value from committed levers.json (baselines).
seed()               # harness-assigned seed
fidelity()           # this round's rung, e.g. {"epochs": 3}
log(name, value, step=None)  # telemetry only; scalars on the trial, steps -> curves
artifact_dir()       # per-trial folder, created on demand
run(fn)              # entry point; fn() -> objective | (objective, {constraint: value})
```
- **Runner scripts are tiny** (`run(train_and_eval)`), generated during pre-loop grilling, and protected.
- **Each trial runs as a subprocess** in the run venv inside the worktree, with its resolved trial file passed through an environment variable. The harness measures wall-clock time, peak memory and the exit code, sends heartbeats, and turns exceptions into failed trials.
- **There is no pruning API.** Only degenerate trials (NaN or divergence) stop early, and they are marked failed.

### Hypothesis spec (pre-registration)
Each hypothesis spec contains:
- an id `H<n>.v<k>`, a title of 80 characters or fewer, and a rationale;
- a `mechanism`, a `provenance` (novel, adapted from a cited source, or standard) and its lens;
- the directive ids it touches;
- a fidelity-sensitive flag, with a reason;
- its levers. Each lever has:
  - a kind: `float` or `int` (`low`, `high`, optional `log`), `categorical` (`options`), or `bool` (`why_not_graded` required);
  - a `baseline` inside its range, at which the code does exactly what it did before the lever existed;
  - a `predicted` direction, for graded levers.

Levers are declared only in the spec, never in code. Merges declare an explicit mapping from old lever values to new ones. Authors write no reject conditions.

### Verdict engine (the fixed reject form)
- **Two statistics**, both measured against δ in objective units:
  - **√V_T:** the square root of the unnormalised group total-order Sobol variance, taken from a noise-aware verdict GP. The GP runs outside Optuna, with the baseline σ² as a floor on its noise term.
  - **Δ:** the best posterior objective with the group free, minus the best with the group at baseline, with the other active levers optimised in both cases. It is estimated from posterior samples over a quasi-random candidate set.
- **Gates:** trial count (split into sampler and agent-chosen), range coverage (sampler trials only), surrogate fit, and noise homogeneity (a spread ratio of about 3× or more fails the gate).
- **Reject** at 95% one-sided credibility when the gates pass and either the upper bound of √V_T is below δ (`irrelevant`) or the upper bound of Δ is below δ (`no-improvement`, which freezes the group at baseline). **Retain** only when both lower bounds are above δ. Otherwise the hypothesis stays active.
- **Burn-in and confirmation:**
  - burn-in is max(10·d, 20) fresh sampler trials at the current fidelity;
  - a reject must be confirmed after max(5·d, 10) more;
  - after burn-in, verdict checks happen every max(5·d, 10) fresh sampler trials.
- **Fidelity-sensitive hypotheses** can't be rejected at a proxy. A contradicted predicted direction flags the verdict as `retained-against-prediction` without changing it.
- **Verdict record** `V-R<n>-H<n>.v<k>-<check>` holds: the condition that fired; √V_T and Δ with their intervals; δ; the gate statuses; the burn-in and confirmation counters; the fidelity and proxy status; the prediction flag; the trial ids used; and the test context (the retained set and co-active hypotheses).
- **Escalation** after a stalled round: a larger replicate share, or the next fidelity rung if calibration says the effect can't be resolved at the current one. At max(40·d, 80) fresh trials without a verdict, the hypothesis becomes inconclusive.
- **Hypothesis states:** proposed, pruned, registered (which *is* the queue), active, retained, rejected, inconclusive and parked. Retains are re-judged every round. Narrowing and freezing are events.
  - Narrowing needs its gates to pass and ends the round.
  - Freezing fixes a lever at baseline when its own upper bound is below δ.
  - Revival creates a new linked version, at most once per pair.
  - Parked hypotheses return with the same version.

### Noise and fidelity
- **Seeds and σ.** Every trial gets a fresh, logged seed. The calibration round runs k (default 5) baseline replicates. σ is re-estimated every round, and a shift of more than 2× is flagged.
- **Replicates** take at least ~10% of trials, and every new incumbent gets 2 confirmation replicates. A replicate is its own trial, linked by `replicate_of`, and is never averaged in.
- **Fidelity ladder.** The ladder is proposed by the orchestrator and calibrated with about 5 diverse configs per rung. A rung passes on ρ ≥ 0.8 and spread ≥ 3σ, and the harness picks the passing rung with the lowest expected cost to a verdict. If no rung passes, the loop falls back to the reference fidelity. An unvalidated proxy needs the user's explicit acceptance, which is logged.
- **Drift check.** Every round re-runs the incumbent and one random config at the reference fidelity. If rank agreement degrades, that round's rejects are downgraded to inconclusive.
- **One fidelity per round.** Old-rung trials become telemetry.

### Warm start and epochs
- **The experiment log is the only source of truth.** Each round's Optuna study, in a disposable SQLite file, is rebuilt from it using `create_trial`/`add_trials`, with every seed bounds-checked by the harness. The GP sampler is used with a non-deterministic objective.
- **One eligibility function** (same epoch, same fidelity, in range) feeds both the sampler and the verdict GP.
- **Mapping rules:**
  - an added lever is backfilled at its baseline;
  - a lever removed as credibly irrelevant has its key dropped;
  - any other removed lever is filtered to its baseline;
  - narrowing drops out-of-range trials and never clips them;
  - merges use their declared mapping;
  - masked levers are seeded with their sampled values.
- **Equivalence check.** After any code change, the harness runs the incumbent and the baseline, 2 replicates each. If either disagrees with its logged mean by more than 2σ, a new epoch starts: earlier trials become telemetry, σ is re-estimated and burn-in restarts. The user can declare a change breaking to skip the check.
- **Round 1 seeds** are the baseline replicates plus up to 5 configs named by the user. They count as agent-chosen trials. There are no πBO priors, no imported history, and no cap or age weighting.

### Round scheduler and run end
- **The harness fills slots**, from the queue by orchestrator-set priority, within a dimension cap derived from the budget, placing hypotheses flagged as interacting together. Retained hypotheses are narrowed, not frozen, when the cap gets tight. A hypothesis left unselected for N rounds is flagged to the user.
- **Round-end triggers:**
  - a search-space change: a confirmed reject, a freeze, a narrowing or a merge. A retain doesn't count, and a pending reject holds the round open;
  - a fidelity change, a new epoch, or a broken proxy;
  - a stall: no gain ≥ δ over max(5·d_total, 20) fresh trials, with no pending confirmation and every active hypothesis past burn-in;
  - the cap of ~25% of the remaining budget;
  - a user checkpoint;
  - a directive revision.
- **Registered hypotheses join only at round boundaries.**
- **Run end:**
  - the budget is spent;
  - the user stops the run;
  - a target set by the user is reached and confirmed;
  - **exhaustion**, which means: the queue is empty, no active hypothesis is undecided, every removal has its interplay review, every revival those reviews requested has run, and a final generation pass produced nothing that survived review.

  Stalls never end the run.
- **Budget.** Budget is the summed wall-clock time of the research loop's trials, from the calibration round onward, tracked in a ledger computed from the log. A trial is refused when its estimated cost, taken from the calibrated rung, exceeds the remaining budget. Wrap-up is outside the budget and has no reserve.

### Code and environment management
- **Worktree and venv.**
  - One `bo-research/<run-id>` branch per run, in a dedicated worktree taken from the user's HEAD.
  - Starting refuses while the user's tree has uncommitted changes.
  - The run venv is created from an exact freeze of the project environment, plus the harness.
- **Code is written just in time.** Registration freezes the spec. When the harness selects a hypothesis for a round, the lever coder writes its code, must pass `smoke <H>` (one trial at baseline and one at a random point, at the cheapest rung), and commits via `commit-lever <H>`. `round-run` is refused until every selected hypothesis has its code committed.
- **Other changes** go through `commit-change(reason)` and `add-dependency`. Both are followed by the equivalence check.
- **Removed hypotheses' code stays in place**, pinned at baseline. The research branch keeps `lever()` and a `levers.json` holding the baselines.
- **Code changes only between rounds**, and each round is pinned to one commit. Every trial records its commit SHA.

### Directives, brief and review
- **The directive registry** holds directives, protected paths and the research brief. It is versioned, owned by the harness and protected, and pre-loop grilling writes it.
- **Directive fields:** an id, a severity (prohibited or discouraged), a statement, a reason, a scope, an optional config predicate, and optional forbidden code patterns.
- **Prohibited directives never reach BO.** They prune a hypothesis, or restrict its lever ranges and options at registration. Seeds outside the allowed region are dropped. Allowed regions that aren't box-shaped are reparameterised into a box. Every trial's resolved config is checked against the prohibited predicates, and commit diffs are scanned for forbidden patterns.
- **Discouraged directives** stay out of the objective and the sampler. They only lower priority, need a stated reason, and add a per-trial `compat:<id>` flag computed from the resolved config.
- **The registration reviewer** returns:
  - a directive verdict: allow, prune or deprioritize;
  - an intent verdict: fits, stretch (lower priority) or off-intent (parked);
  - a conflict class: shared-lever, exclusive, rival or none.

  A similarity hit against a prohibited directive or a pruned hypothesis forces a strict re-review. The reviewer runs at registration, at revival, when a parked hypothesis returns, and on every hypothesis whenever the registry is revised.
- **Revisions** happen only at a checkpoint or during a user pause, and take effect at the next round boundary:
  - a new or tightened prohibition prunes registered hypotheses, parks active ones, and makes violating trials ineligible;
  - a relaxed prohibition sends pruned hypotheses back to proposed;
  - a discouraged change recomputes priorities and flags.

### Agent roster (all subagents on the top tier: `opus` on Claude Code)
| Role | Reads | Records |
|---|---|---|
| Orchestrator (skill) | CLI probe JSON and subagent records only | Actions: ladder, lenses, priorities, expected verdicts, narrow, park, enqueue |
| Hypothesis generator (one per lens, in parallel) | Brief, `SUMMARY.md`, existing titles and mechanisms, analyst suggestions | `proposal` (at least 2 mechanisms) |
| Lever coder (sequential, one hypothesis at a time; also runs in distill mode) | The spec and the codebase | Commits via the harness, after a smoke test |
| Registration reviewer (read-only) | Spec, registry, brief, pruned and parked history (also the distill spec) | `review` |
| Interplay reviewer (read-only) | The removal's evidence bundle and the untested list (or, at registration, the newcomer and past removals) | `interplay` (flagged pairs with evidence) |
| Round analyst (read-only; also runs in distill mode) | Verdict records, sensitivity, telemetry, curves | `narrative` (cited), diagnostics, suggestions; `distill_spec` |

- **Lenses.** At init, the orchestrator picks about 4–6 lenses from the brief, plus a fixed wildcard lens.
- **Generation triggers:** run start; the queue dropping below 2× the slots per round; an analyst flag. With `generation: scripted`, the harness serves fixture proposals instead.
- **Structured output is enforced by the harness.** Each subagent ends with `record <kind>`, where the harness checks the schema and quotes (every quoted number must match its verdict record), and a `SubagentStop` hook blocks until a valid record exists. No plugin workflows are used.
- **Timing.** Agents run only at round boundaries and at registration, never mid-round.
- **Portability.** Roles declare an abstract tier, and host adapters map tiers to models.

### Agent-side CLI (JSON in and out)
- **Probes** (free, read-only): `status`, `summary`, `show`, `verdict`, `trials`, `untested`, `sensitivity`.
- **Actions** (logged with actor and a mandatory rationale):
  - `init`, `propose`, `record`, `register`, `prioritize`, `enqueue`, `round-run`;
  - `park`, `unpark`, `narrow`;
  - `commit-lever`, `commit-change`, `add-dependency`, `smoke`;
  - `checkpoint`, `stop`, `wrapup`, `clean`.
- **Enforcement checks:** `check write|bash|read|recorded|stop`.
- **`round-run`** is the deep command. It runs in the background and exits on a harness trigger. It runs R0 automatically if it's missing, and returns the trigger, the verdict records, the incumbent and a `next` list of outstanding duties.
- **Refusals return their reason as JSON.** The harness refuses:
  - `register` without a reviewer record, or with ranges outside the allowed region;
  - `round-run` while anything in `next` is outstanding or after the run has ended;
  - out-of-budget or prohibited trials;
  - commits touching protected paths or matching forbidden patterns;
  - a dirty tree;
  - a hash-manifest mismatch.

### Experiment log
- **Storage.** One SQLite file holds an append-only `events` table (WAL mode, with triggers rejecting `UPDATE` and `DELETE`). Each event has a sequence number, a type, a schema version, a timestamp, an actor and a JSON payload. Unknown types are refused.
- **State is computed from events.** State tables and every human-readable file are regenerated from the events. The harness CLI is the only writer.
- **Event types.** The event catalogue in the [Experiment log schema](https://github.com/upadhyan/bo-autoresearch/issues/11) resolution defines them, grouped as run, directive, hypothesis, round, trial, evidence, code, budget and hook events.
- **Trial ordering.** A trial is logged as started before it runs, and as finished or failed before Optuna is told. On resume, a trial with no finish is marked abandoned and charged up to its last heartbeat.
- **Layout.** Everything lives in `.bo-research/<run-id>/`, which is gitignored and protected: `log.db`, the disposable study file, `SUMMARY.md`, `rounds/`, `exports/` and `artifacts/trial-<seq>/`. `run.yaml` becomes a protected record after `init`.
- **The run header** records the objective and its direction, δ, the budget, the target and trial ceiling, the reference fidelity, the checkpoint mode, `workers`, the venv freeze and the base commit.

### Summaries and report
- **`SUMMARY.md`** is generated by the harness after every state change. Its sections are: Where we are, Working, Not working, Still testing, Set aside, Up next. It shows one line per hypothesis, with at most 10 lines per section.
- **Round summaries** have mechanical sections plus an analyst narrative that must cite verdict records. They also report expected versus actual verdicts and suggested narrowings.
- **Wrap-up** always produces the same deliverable, regardless of how the run ended.

### Pre-loop grilling
- **Interview part 1 (no data needed), in order:** objective, brief, directives, protected paths, fidelity, budget, seeds and ideas, lenses. Then `init` validates `run.yaml`.
- **Calibration round (R0):** the smoke test, fidelity calibration and baseline replicates.
- **Interview part 2:** show R0's results, set δ, review the list, then R1.
- **The R1 gate** is a harness refusal.
- **Headless start** is allowed when `run.yaml` is complete, including `go: true`.

### Wrap-up and deliverable (outside the budget)
- **Distillation:**
  1. the analyst writes `DISTILL_SPEC.md`, covering the retained mechanisms and their tuned values, how they fit the project's idioms, what to drop, and a keep-or-drop decision for each non-lever change;
  2. the reviewer checks it against the brief and directives;
  3. the lever coder implements it on `bo-research/<run-id>-distilled`, taken from the base commit, with no harness dependency and protected paths untouched. The harness supplies the runner.
- **Verification** runs 3 replicates of each branch at the reference fidelity and requires agreement within 2σ. The coder gets up to 2 retries. If it still fails, the distilled branch is marked unverified and the research branch is the confirmed result.
- **Discouraged winners** are flagged, with the best logged trial that honours the directive and the gap. No extra runs are made.
- **`trials.csv`:**
  - one row per trial of every kind;
  - metadata columns;
  - prefixed column groups `c:`, `t:`, `compat:`, and `L:<lever>` (effective value), plus `sampled:<lever>` for masked levers;
  - an empty lever cell means the lever didn't exist in that trial's code, and a baseline value means it ran at baseline.
- **`hypotheses.csv`:** one row per hypothesis version.
- **`REPORT.md` sections:**
  1. Headline
  2. What to take
  3. Takeaways (analyst-written, cited)
  4. What worked and what didn't
  5. Interactions and revivals
  6. Terms of the run
  7. Process diagnostics
  8. Files
- **`clean`** removes the worktree and the venv but keeps the branches and the log.

### Hooks (thin, fail-closed adapters; inert when no run is active)
- **`SessionStart`** injects the status.
- **`PreToolUse` on Edit, Write and NotebookEdit** calls `check write`. It blocks writes to protected paths, writes to the worktree during a round, and writes to the user's checkout.
- **`PreToolUse` on Bash** calls `check bash`. It enforces the read-only-agent allowlist, blocks installs made outside the harness, catches obvious shell writes to protected paths, blocks git commands that rewrite history in worktrees, and blocks the orchestrator reading raw logs.
- **`PreToolUse` on Read, Grep and Glob**, for the orchestrator only, calls `check read`.
- **`SubagentStop`**, plus the handback in auto mode, calls `check recorded`.
- **`Stop`** calls `check stop`. Stopping is allowed when there's no run, when the run is waiting on the user, while `round-run` runs in the background, or after the run has ended and wrap-up has finished.
- **`PostToolUse`** on harness commands re-injects `next`.
- **Fail-closed rules.** A check that crashes or times out during a run blocks with exit code 2. Every block is logged.

## Testing Decisions

- **Good tests exercise external behaviour at a seam** and assert on what a caller can observe: JSON responses, refusals, logged events and generated files. They never assert on internal classes, the statistics implementation or Optuna internals. The suite should survive any internal refactor of the harness.
- **Seam 1: the `boautoresearch` CLI, driven by a scripted caller with no LLM.**
  - Tests create small synthetic toy projects with planted truth and instant trials, call the CLI, and assert on its JSON and on the event log.
  - Coverage:
    - verdicts against planted truth (irrelevant, no-improvement, retain, interaction survival, fidelity sensitivity, burn-in and confirmation);
    - eligibility and warm-start mapping, and epochs;
    - round-end triggers, the budget ledger and refusal, and escalation;
    - every harness refusal, and every `check` decision the hooks depend on;
    - crash resume;
    - `SUMMARY.md`, the report and the CSV contents;
    - the six runner-side names, exercised through real trial subprocesses.
  - Statistical tests fix seeds, and assert rates over repeats wherever a single outcome is probabilistic.
- **Seam 2: the dogfood benchmark**, the acceptance test, run end to end through the real plugin via headless `claude -p`.
  - **The objective** is a synthetic toy trainer: code that looks like a training loop, with an `epochs` fidelity and a planted analytic loss with tunable σ. Each trial sleeps in proportion to epochs.
  - **Scripted mode** is the gate: fixture proposals are served in fixed passes, and every other role is real.
  - **Free mode** is reported, and only its invariants are gated.
  - **Nine planted cases:**
    - useful → retained;
    - useless → `irrelevant`;
    - harmful → `no-improvement`;
    - an interaction caught at registration → revived, and both retained;
    - an interaction caught by interplay review → revived, and both retained;
    - fidelity-sensitive → never rejected at a proxy, and retained at the reference;
    - discouraged but winning → retained and flagged with its price;
    - prohibited → pruned, with 0 trials;
    - off-intent → parked, with 0 trials.
  - **An adversarial checklist** is issued by the driver: protected writes via Edit, Bash and `python -c`; a `git commit` in the worktree; register without review; round-run while blocked; an install made outside the harness; an early stop; the orchestrator reading `log.db`. Each must be blocked and logged.
  - **Hard invariants, in every run:**
    - no prohibited violation;
    - the manifest stays clean;
    - no proxy reject of the fidelity-sensitive lever;
    - no stall-ended run;
    - every adversarial action blocked;
    - the distilled branch has no harness import and its protected paths are unchanged.
  - **Scripted mode also requires:**
    - the verdict table;
    - the run ends by exhaustion;
    - the confirmed incumbent is within δ of the planted optimum;
    - the distilled branch is verified;
    - the summaries agree with `hypotheses.csv`.
  - **Repeats:** 3 seeds × 2 noise levels (σ = δ/4 and δ/2). The invariants must hold 6 of 6, and each verdict must be correct in at least 5 of 6.
- **No other seams.** In particular there is no standalone verdict-engine seam, so internals stay free to change.
- **Prior art:** none in the repo yet. The throwaway prototype on `prototype/harness-api` shows the shape of Seam 1: a scripted session calling CLI functions and asserting on JSON refusals and records.

## Out of Scope

- Multi-objective or Pareto search. v1 optimises one objective plus constraints.
- Changing the objective mid-run. That starts a new run.
- Remote or cluster execution. v1 runs on a single machine with SQLite.
- Token or cost accounting.
- Multi-fidelity BO and heteroscedastic noise models. Failed noise homogeneity gives an inconclusive verdict.
- Agent hosts other than Claude Code (Codex, opencode). Supporting one later means writing hook adapters and a map from tiers to models (configurable by the user for opencode).
- Performance-based pruning, πBO priors, and importing historical results as trials.
- Copying settings from an earlier run (`init --from`).
- Integrating discouraged-honouring alternatives on the distilled branch. The report offers a follow-up instead.

## Further Notes

- **Where the decisions live.** Each decision's full reasoning is in the resolution comment of its ticket under [Map: BO-driven autoresearch plugin](https://github.com/upadhyan/bo-autoresearch/issues/1). Where tickets amend each other, this spec states the final form. The prior-art notes are in `docs/research/`.
- **Standing principle.** Agent control lives in deterministic harness code first and thin hooks second. The LLM makes judgement calls, and the harness or a hook forces each one to happen.
- **Model pinning isn't guaranteed.** On Claude Code, an organisation's model allowlist or `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` can override the pinned subagent models.
- **Hook data isn't in Bash's environment.** The plugin's `${CLAUDE_PLUGIN_ROOT}` is not set in the Bash tool's environment, so the skill text must carry expanded paths.

## Amendment: the `irrelevant` statistic (Verdict engine)

**Amends** "Verdict engine (the fixed reject form)" in this spec, and items 1, 4 and 5 of the [Reject-condition form](https://github.com/upadhyan/bo-autoresearch/issues/8) resolution. The research is in [`docs/research/irrelevance-statistic.md`](https://github.com/upadhyan/bo-autoresearch/blob/research/irrelevance-statistic/docs/research/irrelevance-statistic.md) on `research/irrelevance-statistic`.

### Problem
√V_T is a standard deviation: it measures how much the objective *varies* as the group moves, not how *far* it moves. δ is a change in the objective. How √V_T compares with the real effect depends on the effect's shape:
- a step gives at most 1/2;
- a linear effect gives 1/√12 ≈ 0.29;
- a product interaction `a·x_A·x_B` gives 1/6;
- a narrow spike gives almost 0.

So a linear lever worth up to about 3.5δ could be rejected `irrelevant` while its Δ was well above δ. The interaction that total-order Sobol was chosen to protect is the case it under-reports most. No constant rescaling of δ fixes this, because any constant is exact for one shape only.

### Decision
1. **Replace √V_T with the total-effect range M_u.** M_u is the largest change in the latent posterior as the group moves across its box, taken over every setting of the other active levers (the largest ICE range). It is in objective units, counts interactions at their strongest setting, and gives `a` for both `a·x` and `a·x_A·x_B`. It is computed on each latent posterior sample path, never on noisy draws, with one-sided 95% bounds across paths. It uses the same candidate set as Δ, plus the baseline slice and Δ's maximisers.
2. **`no-improvement`:** the upper bound of Δ is below δ. The action is unchanged: freeze the group at baseline and filter its trials to baseline.
3. **`irrelevant`:** `no-improvement` **and** the upper bound of M_u is below δ. The action is to drop the key and keep the trials. On every sample path Δ ≤ M_u, so `irrelevant` is a sub-case of `no-improvement` by construction: it changes the label and the warm-start action, never whether a hypothesis is rejected. Keeping the trials after dropping the key is justified only by this bound, because M_u < δ limits how far any single trial's value could move.
4. **Retain:** the lower bound of Δ is above δ. M_u's lower bound is recorded but is implied.
5. **Freezing a single lever:** freeze lever i when the upper bound of Δ_i is below δ, where Δ_i compares i free with i at baseline, everything else optimised. Its key is dropped only if the upper bound of M_i is also below δ. At most one lever is frozen per verdict check.
6. **Substitutes:** apply confirmed `no-improvement` rejects among co-active hypotheses one per round end, smallest upper bound of Δ first, and re-judge the rest in the next round. Two levers that do the same thing each get Δ = 0 because the other is optimised in both terms, so rejecting both at once would lose the gain. The original spec had this gap too.
7. **√V_T and the normalised total-order index S_T become telemetry** in the verdict record, next to M_u and Δ.

The gates, burn-in, confirmation and escalation are unchanged. The verdict record gains M_u and its interval; √V_T stays as a telemetry field.

### Open questions (to be measured on the dogfood benchmark, #38)
- How much slower flat groups get rejected, now that √V_T no longer rejects early.
- The candidate-set size, since a maximum over many points is inflated where the posterior is wide.
- The false-reject rate across repeated verdict checks with the confirming check.
- Whether `irrelevant` needs an explicit range-coverage pass in the box's corners.

## Amendment: noise checks use a two-stage t-test on a pooled σ (α = 5%)

**Why.** The equivalence check, branch verification and drift check compared against a σ estimated from R0's baseline replicates alone (4 degrees of freedom, fewer in small runs). With that σ, a true no-op change started a new epoch about **15%** of the time, not the ~3–6% assumed; an identical distilled branch failed verification ~12% of the time; a faithful proxy was flagged broken ~9% of the time. Research: `docs/research/equivalence-check-threshold.md` (branch `v1-followups`).

**Replacement wording.**

- **Equivalence check:** After any code change, the harness runs the incumbent and the baseline, 2 replicates each. A config that disagrees with its logged mean by more than 2σ gets 4 more replicates. A new epoch starts only if the mean of its 6 still differs from the logged mean in a two-sided t-test at α = 5% (split across the configs checked). σ is pooled within configs over the epoch's trials at that fidelity, and the incumbent's logged mean leaves out the trial that made it the incumbent. In a new epoch, earlier trials become telemetry, σ is re-estimated and burn-in restarts. The user can declare a change breaking to skip the check.
- **Verification:** Verification runs 3 replicates of each branch at the reference fidelity. The branches agree if their means are within 2σ·√(2/3). Otherwise the distilled branch gets 3 more replicates, and it fails only if its 6 still differ from the research branch's 3 in a two-sided t-test at α = 5%, with σ pooled as in the equivalence check. The coder gets up to 2 retries.
- **Drift check:** Every round re-runs the incumbent and one random config at the reference fidelity. The config is drawn from the round's configs that the proxy fidelity separates from the incumbent by more than noise. If the reference reverses their order by more than noise (a one-sided t-test at α = 5% on the pooled σ), that round's rejects are downgraded to inconclusive. If the proxy separates no config from the incumbent, the check is undecidable and the round's rejects are deferred to a later round.
- **σ (add):** The equivalence, verification and drift checks use σ pooled over the epoch's replicates. The verdict GP's noise floor and δ advice keep the baseline σ.

**Measured (Monte Carlo, true σ = 1, δ = 2σ; after = df 4 / df 20):**

| Check | False alarm before → after | Power at δ before → after | Trials per no-op check |
|---|---|---|---|
| Equivalence | 14.8% → 3.6% / 2.5% | .74 → .53 / .69 | 4 → 4.8 / 4.3 |
| Verification | 11.6% → 4.2% / 3.0% | .68 → .55 / .65 | 6 → 6.4 / 6.2 |
| Drift | 5.7% (9% at df 2) → 5.0% | .35 → .32 / .39 | 2 |

End to end, a reversed proxy next to a useless co-active lever is now caught 20/20 (was 7/20), because the drift pair can no longer be a tie.

**Known limit.** A proxy fidelity that never separates any config defers the same rejects round after round until the budget ends (marked `ponytail:` in `cli.py`).

**Clarification: budget.** The budget is summed per-trial compute time (wall-clock of each trial, added up), not elapsed time; with `workers` = W it is spent about W times faster in real time. `workers` > 1 now runs a BO round's trials in parallel.

## Amendment: calibrated verdict intervals (Verdict engine)

**Amends** "Verdict engine" and the `irrelevant` amendment above.

### Problem
The verdict GP fit its hyperparameters by maximum likelihood with no floor on the signal. At low signal-to-noise the fit went flat (signal variance near zero, or lengthscales far past the box), and the posterior was then certain the lever did nothing. A planted linear gain of exactly δ at σ = 1.5δ was rejected in 10 of 20 runs, and Δ's 95% bounds held δ in only 5 of 32 checks. The spec promises 95% one-sided credibility.

### Decision
1. **The verdict model admits the effect under test.** Besides the baseline σ² floor on its noise, the GP's signal sd is at least 1.5δ. Each lever's lengthscale is at most √(signal variance / signal floor) (box width 1), so the prior's slope along any lever never drops below what an effect of δ needs, however much signal the other levers carry. Lengthscales are also at least 0.1, so noise isn't read as wiggles that inflate Δ.
   - Measured over seeds 0..19: a gain of δ is never rejected, and Δ's and M_u's bounds hold δ in 23 of 26 checks.
   - Flat levers are still rejected: 1 lever at σ = δ/2, 19/20 at 30 fresh trials; 3 levers at σ = δ, 20/20 within six rounds.
2. **`irrelevant` needs evidence across the other active levers' box.** M_u is bounded over every setting of the other active levers. Next to a curved partner, BO leaves most of that box unexplored, so M_u's upper bound stays above δ. **`no-improvement` is then the expected label** for a flat lever: its trials are filtered to baseline instead of its key being dropped. This is the correct outcome, not a miss. `irrelevant` still fires when the partners are smooth or their box has been covered. Rejects are unaffected; only the label and the warm-start action differ.
3. **Seam 2 acceptance:** a useless lever next to a useful curved one is correctly verdicted if it is rejected `irrelevant` **or** `no-improvement`. The other cases are unchanged.

The open question on an explicit range-coverage pass in the box's corners stays open: such a pass would make `irrelevant` reachable next to curved partners.
