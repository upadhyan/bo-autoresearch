## Question

What is the structure of the experiment log? Cover:
- The hypothesis registry: rationale, levers, reject conditions, state, verdict and reason.
- Per-trial records: lever values, objective, telemetry, artifact path.
- Per-round summaries.
- A replayable log of agent decisions.
- The **expected** verdict for each hypothesis, recorded before each round runs, adapted from 2608.00316, which asks for the expected outcome before each *trial*.

Decide how it relates to Optuna's own storage, what format it uses (for example JSONL plus SQLite), and how crash-safe resume works.

**upadhyan** (2026-09-28T21:45:56Z):

## Resolution

**Gist:** the experiment log is an append-only stream of **events**, stored in one SQLite table. Every piece of state is computed from those events, and the harness CLI is the only thing that writes to it. Optuna's storage is a disposable cache rebuilt from the log. Trials are logged before they run and before Optuna hears their result, so resuming after a crash is mechanical. On top of the log, the harness regenerates a short, human-readable **research summary** of what has been tested, what is working and what isn't.

### Storage
1. **`log.db` holds one `events` table**, in SQLite with WAL mode. Triggers make it append-only: `UPDATE` and `DELETE` raise an error.
   - **Each event has:** a sequence number, a type, a schema version, a timestamp, an actor (harness, orchestrator, a named subagent, user or hook), and a JSON payload.
   - **Unknown event types are refused.** Older schema versions are upgraded when read.
2. **State is computed from the events.** State tables are rebuilt from them and are never edited directly. That state covers:
   - the hypothesis registry and each hypothesis's state;
   - the directive registry and research brief;
   - the budget ledger;
   - the incumbent;
   - the eligibility inputs.

   Human-readable exports, such as `trials.csv` and the markdown summaries, are regenerated from the events too.
3. **The harness CLI is the only writer.** Every command it runs is logged with its actor, its inputs by event id, and a rationale.
   - "Replayable" means the state can be recomputed exactly from the events. It does not mean re-running the LLM.
   - Hook blocks are logged as `hook_blocked` events.
   - Subagent transcripts are stored by path.

### Relationship to Optuna
4. **`studies.db` is disposable.** It's rebuilt from the log at the start of each round and on resume, as decided in [Warm-start policy](https://github.com/upadhyan/bo-autoresearch/issues/9).
   - `trial_started` is logged before the trial runs, with its assigned values, seed, fidelity, commit, epoch and estimated cost.
   - `trial_finished` or `trial_failed` is logged before Optuna is told the result.
   - If the log and Optuna disagree, the log wins.

### Resuming after a crash
5. **A trial with a start event but no finish** gets `trial_abandoned`. It's charged to the budget up to its last heartbeat, and it's never retried automatically.
6. **A failed trial**, meaning the code raised an error, is charged to the budget but gives no objective value. Failure rates are reported per hypothesis.
7. **Orchestrator restart:** a `SessionStart` hook injects `harness status`, a snapshot of the current state computed from the log. The agent never reconstructs the state from memory.

### Expected verdicts
8. **Before each round,** the orchestrator records an expected verdict (retain, reject or undecided) for every active hypothesis, with a one-line reason.
   - The round-start `PreToolUse` hook blocks until every active hypothesis has one.
   - Expectations never affect verdicts. The final deliverable reports how often they were right.
9. **Agent-chosen trials** must log an expected objective. Sampler trials don't need one.

### Summaries
10. **Round summary:** `rounds/NNN.md`, plus a `round_summary` event.
    - **Mechanical sections**, produced from the log: the end trigger, verdict records, incumbent, σ, budget, the best configuration that honours each discouraged directive, suggested narrowings, expected versus actual verdicts, and proposed directives.
    - **An orchestrator narrative**, which must cite verdict record ids. The quote-check hook enforces this.
11. **Research summary** (`SUMMARY.md`), which the user asked for: a short, human-readable, current picture of the whole run.
    - **Written by the harness, not an LLM.** It is regenerated from the log after every verdict check, round end and state change, so it never drifts from the evidence.
    - **Every hypothesis gets a plain-language title** of 80 characters or fewer, required at registration. The summary shows one line per hypothesis, using that title.
    - **Sections, in this order:**
      - **Where we are:** the incumbent against the baseline, with the gain in objective units and in δ; budget used and remaining; the current round; and the run-end reason, once there is one.
      - **Working:** retained hypotheses, with the improvement Δ and its interval.
      - **Not working:** rejected hypotheses, with the reason in words ("doesn't matter" or "matters, but doesn't help"). If a revival is planned, that is noted.
      - **Still testing:** active hypotheses, with their progress toward a verdict.
      - **Set aside:** parked hypotheses (including off-intent ones), pruned hypotheses and inconclusive hypotheses, each with its reason.
      - **Up next:** the number of queued hypotheses and the first 3 by priority.
    - **Length:** each section is capped at 10 lines, with a pointer to the round summaries or `trials.csv` for the rest. There are no statistics beyond the one effect interval per line.

### Layout
12. **`.bo-research/<run-id>/`** lives in the main repo. It's gitignored and a protected path, and sits outside the worktree so it's never committed. It contains:
    - `log.db` and `studies.db`;
    - `SUMMARY.md`;
    - `rounds/`;
    - `exports/`;
    - `artifacts/trial-<seq>/`: the resolved config, stdout/stderr, metrics and any learning curves.

    Every artifact is kept.

### Run header and ids
13. **`run_started`** records the objective and its direction, δ, the budget, reserve, optional target and trial-count ceiling, the reference fidelity, the checkpoint mode, the venv freeze and the base commit.
14. **Ids:**
    - trial: a global sequence number;
    - hypothesis: `H<n>.v<k>`;
    - round: `R<n>`;
    - verdict record: `V-R<n>-H<n>.v<k>-<check>`.

### Event catalogue
The payloads combine this ticket's decisions with the notes posted here from earlier tickets.
- **Run:**
  - `run_started`, `run_ended` (with its reason), `checkpoint`, `user_pause` and `user_stop`.
- **Directives:**
  - `registry_revised`, which versions directives, protected paths and the research brief;
  - `directive_proposed`.
- **Hypotheses:**
  - `hypothesis_proposed`, carrying the title, rationale, `mechanism`, `provenance`, levers with ranges and baselines, predicted directions, the fidelity-sensitive flag and the directive ids it touches;
  - `reviewer_record`, with the directive verdict, intent verdict, conflict class and rationales;
  - `hypothesis_registered`, with its commit SHA;
  - state transitions: `activated`, `retained`, `rejected`, `inconclusive`, `parked` and `pruned`;
  - `revived`, with its lineage;
  - `narrowed`, `frozen`, `merged` (with the value mapping), and masking or rival links;
  - `escalated`.
- **Rounds:**
  - `round_started`, carrying the commit, fidelity and search space;
  - `expected_verdict`;
  - `round_ended`, with its trigger;
  - `round_summary`.
- **Trials:**
  - `trial_started` and `trial_heartbeat`;
  - `trial_finished`, carrying the objective, constraints, telemetry, `compat:<id>` flags, wall-clock time and artifact path;
  - `trial_failed` and `trial_abandoned`;
  - `prohibited_check_refused`.

  Replicates carry `replicate_of`, and masked levers log both their sampled and effective values.
- **Evidence:**
  - `noise_estimate` (σ);
  - `fidelity_calibration`, with ρ, resolvability and the chosen rung;
  - `proxy_accepted_unvalidated`;
  - `verdict_record`, carrying the condition that fired, √V_T and Δ with their intervals, δ, gate statuses, burn-in and confirmation counters, the prediction flag, the trial ids used and the test context;
  - `removal_event`;
  - `interplay_review`, with flagged pairs and cited evidence.
- **Code:**
  - `commit_change`, with its reason;
  - `dependency_added`;
  - `equivalence_check`;
  - `epoch_started`, including breaking changes the user declares;
  - `distilled_branch_built`;
  - `final_confirmation`, recording which branch it ran on, plus the best honouring configurations.
- **Budget:** charged from each trial's wall-clock time and refused starts. The ledger is computed from the events.
- **Hooks:** `hook_blocked`.

### Knock-on for open tickets
- **Runner harness API:** the CLI is the only writer. It needs event appends, state rebuilds, `harness status`, rebuilding `studies.db` from the log, logging trials before and after they run, heartbeats and abandoned trials, regenerating `SUMMARY.md` and the round summaries, and the `.bo-research/<run-id>/` layout.
- **Enforcement hooks:** add a `SessionStart` hook that injects `harness status`, a round-start block until expected verdicts are recorded, logging of every block as `hook_blocked`, and protection of `.bo-research/`.
- **Agent roster and contracts:** proposers must give every hypothesis a plain-language title of 80 characters or fewer. The orchestrator must record expected verdicts and an expected objective for agent-chosen trials. The round narrative must cite verdict record ids.
- **Final deliverable:** it can build on `SUMMARY.md` as the executive view. It should also report how accurate the expected verdicts were, and failure rates per hypothesis.
