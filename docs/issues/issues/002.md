## Question

How do Optuna's primitives behave when the search space changes between rounds?
- What happens with `study.add_trial` / `create_trial` / `enqueue_trial` when the distributions differ from the ones the trials were run under (widened, narrowed, new param, dropped param, fixed param)?
- How do TPESampler (including `multivariate`/`group`), GPSampler and CMA-ES handle a dynamic space, conditional params, and prior trials that fall outside the current bounds?
- What does `constraints_func` support per sampler?
- What does crash-safe resume with RDB/SQLite storage give us?

Cite the Optuna docs and source code. Findings feed **Warm-start policy** and **Runner harness API**.

**upadhyan** (2026-09-25T03:06:19Z):

**Resolved.** The full findings, checked against Optuna v5.0.0 with source links down to the line and a SQLite probe, are in [docs/research/optuna-changing-search-spaces.md](https://github.com/upadhyan/bo-autoresearch/blob/research/optuna-changing-search-spaces/docs/research/optuna-changing-search-spaces.md).

**Gist:** Optuna's model-based samplers only use prior trials whose distributions exactly match the current ones. So the warm start should be a fresh study per round, seeded with `create_trial` + `add_trials` from prior trials rewritten to that round's exact lever distributions.

**Key facts for Warm-start policy and Runner harness API**
1. **Model-based samplers need identical distributions.** Multivariate TPE (the v5 default), GP and CMA-ES model a param jointly only while every finished trial has an *identical* distribution for it, bounds included. Any change to a bound, or adding or dropping a lever, takes that param out of the joint model: TPE falls back to modelling it alone, and GP and CMA-ES sample it at random.
2. **Use one study per round, in the same SQLite file.** Seed it with prior trials rewritten to that round's exact distributions and lever set.
3. **`create_trial` validates strictly.** A value outside its distribution, or mismatched keys, raises `ValueError`. A narrowed range means dropping trials that fall outside it, an added lever means filling in a baseline value, and a removed lever means deleting its key.
4. **`enqueue_trial` validates loosely.** An out-of-range value only warns, and the trial runs with it anyway. Unused keys are ignored and missing levers are sampled normally. The harness must check the bounds of its seeds itself.
5. **SQLite is stricter than in-memory storage.** Within one study it rejects a change to a param's type, `log` flag or categorical choices; bounds and `step` may change. In-memory storage skips these checks on `add_trial`, so test on SQLite.
6. **Stale out-of-range trials skew TPE.** Old trials left in the study pull samples towards the edge of a narrowed range. In the probe, narrowing to [0,5] with the old optimum at 15 gave samples of 4.85–5.0.
7. **TPE `group=True` hides new-lever interactions.** It keeps the first-seen distribution, so widened bounds are never explored, and it models a lever added in a later round separately from the older ones. Interactions between new and old levers are not learned.
8. **Constraints changed in v5.** `constraints_func` is deprecated; use `trial.set_constraint` or `create_trial(constraints=...)`. TPE tolerates missing or renamed constraints. GP raises unless every completed trial has the same number of constraints. CMA-ES ignores constraints.
9. **Warm-start trials count toward `n_startup_trials`.** Don't copy a trial's internal attributes verbatim, because that also brings in CMA-ES's saved optimizer with the old dimensions. Copy only params, values, constraints and lineage attributes.
10. **Resume keeps finished trials, not sampler state.** SQLite commits every write, so `load_if_exists=True` brings back all finished trials, but the sampler's random state is lost unless it is pickled. A killed trial stays `RUNNING` unless heartbeat is on, which works only with `optimize()`, not ask/tell; otherwise the harness must mark stale trials failed at startup. SQLite supports one writing process only.
