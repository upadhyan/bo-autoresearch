## What to build
The thinnest path from an empty project to one logged trial:
- `boautoresearch init` from a bare `run.yaml` (objective, direction, budget) creates the run's worktree on `bo-research/<run-id>`, a dedicated venv (an exact freeze of the project environment plus the harness), and `.bo-research/<run-id>/`. It refuses a dirty user tree.
- The append-only experiment log: an SQLite `events` table whose triggers reject UPDATE and DELETE. Each event has a sequence number, type, schema version, timestamp, actor and JSON payload. State tables are rebuilt from events, and the harness CLI is the only writer.
- The six runner-side names: `lever`, `seed`, `fidelity`, `log`, `artifact_dir`, `run`.
- One baseline trial runs as a subprocess. It is logged as `trial_started` before it runs, and as `trial_finished` or `trial_failed` afterwards. The harness measures wall-clock time, peak memory and the exit code.
- The `status` and `trials` probes, and a minimal `trials.csv` export.

## Acceptance criteria
- [ ] `init` on a toy project creates the worktree, venv and run folder, logs `run_started`, and refuses when the user's tree is dirty.
- [ ] An `UPDATE` or `DELETE` on `events` fails, and rebuilding state from events alone reproduces `status` exactly.
- [ ] A baseline trial runs as a subprocess, and its start and finish events appear in order, with wall-clock time and artifact path.
- [ ] A runner that raises produces `trial_failed` with no objective value.
- [ ] Running the runner outside the harness uses the `levers.json` defaults and prints the result.
- [ ] Every action requires a rationale and logs its actor. Probes are not logged.
- [ ] Refusals are returned as JSON with a reason.
