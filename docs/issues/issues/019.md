## Question

Which invariants do plugin hooks hard-block, on which hook events, and what does each hook read to decide?

Standing preference: agent control goes in hooks and deterministic harness processes. The LLM makes judgement calls, and hooks force them to happen.

Hooks already decided:
- a `Stop` hook that blocks early stopping, unless the budget ledger shows budget spent, target confirmed or exhaustion, or the user has stopped the run;
- a `PreToolUse` hook on round start that blocks after the run ends, or while a removal event lacks its interplay review;
- a hook on the verdict command that injects the interplay-review requirement;
- the judge quote check on `SubagentStop`.

These come from [Round termination rule](https://github.com/upadhyan/bo-autoresearch/issues/10) and [Reject-condition form](https://github.com/upadhyan/bo-autoresearch/issues/8).

Still open:
- Which other invariants deserve a hook, e.g. a hypothesis entering the loop without a baseline, a predicted direction or frozen reject conditions, a trial finishing without an artifact, the agent editing harness code or untouchable code, or agent-chosen trials exceeding their cap?
- How do hooks read state: through the experiment log, or through a harness CLI?
- Plugin agents can't carry their own hooks, so which checks must be plugin-level `hooks/hooks.json`, and which must be workflow `agent({schema})` calls?

## Resolution

**Gist:** hooks are thin, fail-closed adapters to `boautoresearch check …`, and they stay inert in any repo without an active run. They cover only what the harness can't see: file writes and reads, Bash commands, subagents finishing, stopping, and injecting context. Everything else is a harness refusal. A hash manifest of protected paths is the deterministic backstop for anything a Bash parser misses.

### Moved out of hooks, into the harness
These items were listed as "already decided" hooks, but later tickets moved them into the harness:
- **The round-start blocks** (a run that has ended, a missing interplay review, a missing expected verdict) are now `round-run` refusals.
- **The judge quote check and the reviewer schema check** now happen at `boautoresearch record` ([Agent roster and contracts](https://github.com/upadhyan/bo-autoresearch/issues/14)).
- **The hook on the verdict command** is replaced by the `next` list, plus the re-injection hook below.

The other candidate invariants are also harness refusals: a missing baseline, a missing predicted direction or reject condition, a trial with no artifact, and agent-chosen trials over their cap.

### Hook table
Every hook calls `boautoresearch check …`, which logs each block as `hook_blocked`.

| Event (matcher) | Check | Blocks |
|---|---|---|
| `SessionStart` | `status` | Never. It injects the run's status and `next` list. |
| `PreToolUse` (Edit, Write, NotebookEdit) | `check write <path> --agent <type>` | Writes to protected paths (including `.bo-research/`, the registry, the brief, the runner and the run venv); any write to the worktree while a round is running (this doesn't apply during wrap-up, when the distill-mode coder writes the distilled branch's worktree under the same protected-path rules); and any write to the user's own checkout outside the run worktrees (the `run.yaml` draft before `init` is the one exception). |
| `PreToolUse` (Bash) | `check bash <cmd> --agent <type>` | See the Bash list below. |
| `PreToolUse` (Read, Grep, Glob; orchestrator only) | `check read <path>` | Reading `.bo-research/artifacts/` or `log.db`. |
| `SubagentStop` (plugin agent types), plus `PreToolUse` on `SubagentHandback` in auto mode | `check recorded <agent_id>` | A subagent finishing without a valid record. |
| `Stop` | `check stop` | See "When Stop is allowed" below. |
| `PostToolUse` (Bash `boautoresearch *`) | `next` | Never. It re-injects the `next` list after every harness command. |

**The Bash check blocks:**
- for the read-only agents, anything except `boautoresearch` probes and `record`;
- installs made outside `add-dependency`;
- obvious shell writes to protected paths: redirects, `sed -i`, `rm`, `mv`, `cp`;
- history-changing git commands in any run worktree: `commit`, `reset`, `rebase`, `checkout`, `stash`, `merge`, `push`. Commits go through the harness only. Read-only git (`diff`, `log`, `show`) is allowed;
- for the orchestrator, reads of `log.db` or artifacts through `sqlite3`, `cat` and similar.

### Backstop for writes made through Bash
1. **A hash manifest of every protected path** is recorded at `init`, and re-checked before every round and at every commit, including distillation commits. On a mismatch the harness refuses the action and names the file.
   - This catches changes the best-effort Bash parser misses, such as a write through `python -c`.

### When `Stop` is allowed
2. **`check stop` allows stopping when:**
   - there is no active run in this repo;
   - the run is waiting on the user: the pre-loop interviews, a checkpoint pause, or a user pause;
   - a `round-run` is running in the background, so the agent will be woken when it finishes;
   - the run has ended (budget, user, target or exhaustion) **and** wrap-up is finished (distillation, verification and report), or `--no-confirm` was given.

   Otherwise it exits 2, with the `next` list as the reason.

### Failure handling and scope
3. **Inert without a run.** Each adapter first checks whether there's an active run in the repo, and exits 0 at once if there isn't.
4. **Fails closed during a run.** If there is an active run and the harness check crashes or times out, the adapter exits 2, with the error as the reason.
5. **Fast.** Adapters are standard-library Python scripts in `hooks/`, run with `python3 ${CLAUDE_PLUGIN_ROOT}/hooks/<name>.py`, and they call the run venv's `boautoresearch` CLI.
6. **Where they live.** Every hook is plugin-level in `hooks/hooks.json`, because plugin agents can't carry their own hooks. They are scoped to particular agents by `agent_type`. No workflows are used.
