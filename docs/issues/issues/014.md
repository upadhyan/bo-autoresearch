## Question

Which subagents exist, what does each read, what structured verdict does each return, and which model tier does each use? Candidates are a log analyst, a hypothesis critic or judge, a lever coder, and a hypothesis generator. The orchestrator reads only verdicts.

From 2608.00316:
- Judges must cite reject conditions against telemetry, so they can't rubber-stamp. 2608.00316 has no judges; this answers its agent's lazy deference to the surrogate.
- Hypothesis generation should be pushed toward variety. 2608.00316 lists tool-use inertia as an open problem rather than solving it.
- Model tier matters more than reasoning effort, so keep judge output tightly structured.

Also decide when the orchestrator spends an agent versus letting BO keep searching.

**upadhyan** (2026-09-28T22:03:06Z):

## Resolution

**Gist:** the plugin has six roles: the orchestrator skill plus five subagents. Every subagent ends by calling `boautoresearch record`, which validates its output, and a `SubagentStop` hook won't let a subagent finish until that record exists. No workflows are needed. Every role runs on the top model tier. Generation runs as parallel **lenses** to force variety. Lever code is written just in time, when a hypothesis is picked for a round, and has to pass a smoke test. Agents run only at round boundaries and at registration, never during a round.

### Roster
| Role | Kind | Reads | Produces (through `record`) |
|---|---|---|---|
| **Orchestrator** | Skill in the main session | CLI probe JSON and subagent records only | Actions through the CLI: the fidelity ladder at init, lenses, priorities, expected verdicts, narrow, park, enqueue |
| **Hypothesis generator** | Subagent, one per lens, in parallel | Research brief, `SUMMARY.md`, titles and mechanisms of all existing hypotheses, the analyst's suggestions | `proposal`: full hypothesis specs, covering at least 2 mechanisms |
| **Lever coder** | Subagent, one per hypothesis, run one after another | That hypothesis's spec, and the codebase | Code committed via `commit-lever <H>`, after `smoke <H>` passes |
| **Registration reviewer** | Subagent, read-only | Hypothesis spec, directive registry, research brief, pruned and parked history | `review`: directive verdict, intent verdict (fits, stretch or off-intent) and conflict class |
| **Interplay reviewer** | Subagent, read-only | The removal's evidence bundle and the untested list. When run at registration, the newcomer and past removals instead. | `interplay`: flagged pairs, each with a reason that cites evidence |
| **Round analyst** | Subagent, read-only | Verdict records, `sensitivity`, telemetry and curves for the round | `narrative`: a cited narrative, diagnostics per hypothesis (e.g. "lever sits at the edge of its range"), and suggestions (narrow or widen, follow-up ideas for the generator) |

The log analyst and the judge were merged into the round analyst. The fidelity ladder and expected verdicts stay with the orchestrator.

### Enforcing structured output
1. **The harness enforces output, so no plugin workflows are needed.**
   - Each subagent's last act is `boautoresearch record <kind> --file out.json`.
   - The harness checks the schema and the quotes (every quoted number must match its verdict record), and refuses on any mismatch. The subagent sees the refusal and fixes its output.
   - A `SubagentStop` hook, matched on the plugin's agent types, blocks the subagent from finishing until the harness confirms a valid record exists for it.
   - The harness's `next` list and its refusals already fix the order things happen in.
2. **The record kinds** are `proposal`, `review`, `interplay`, `narrative` and `expected`. The orchestrator records `expected` itself.

### Model tier
3. **Every subagent is pinned to `opus`**, with high effort for the generator and both reviewers. The orchestrator uses the session's model. Cost isn't a concern, and tier matters more than effort. The lever coder stays on the top tier too, because a bug in lever code costs a whole epoch.
4. **Other agent hosts.** Roles declare an abstract **tier** (`top`) rather than a model name, and each host adapter maps tiers to its own provider's model: on Claude Code, `top` means `opus`.
   - The mapping for Codex and opencode is decided when those hosts come into scope. Opencode supports many providers and models, so it will need a user-configurable tier-to-model map, possibly with a check that the chosen model can handle the structured `record` output.
   - This is noted in the map's Out of scope entry for other hosts.

### Variety in generation
5. **Lenses.**
   - At init, the orchestrator chooses about 4–6 lenses from the research brief. For ML these might be data, optimisation, architecture, regularisation and systems. For speeding up an implementation they might be algorithmic, memory, parallelism and compiler.
   - There is always one extra **wildcard** lens: "propose what the other lenses wouldn't".
   - One generator instance runs per lens, in parallel. Each must return proposals spanning at least 2 mechanisms.
   - Duplicates are caught by the reviewer's conflict and similarity checks.
   - The number of lenses and the number of proposals per lens are set in pre-loop grilling.
6. **When generation runs.** The harness's `next` list requests a generation pass:
   - at run start;
   - whenever the registered queue drops below 2× the slots per round;
   - when the analyst flags something new, such as a retain or a surprising interaction.

   The orchestrator can also request one with a rationale.
7. **Exhaustion** (amends [Round termination rule](https://github.com/upadhyan/bo-autoresearch/issues/10), condition iv): the final generation pass must produce nothing that survives review. The harness can see that check, so exhaustion never rests on the orchestrator's say-so.

### Lever code
8. **Code is written just in time** (amends [Code-change management](https://github.com/upadhyan/bo-autoresearch/issues/12), item 4).
   - Registration freezes the spec and its reject conditions.
   - Code is written when the harness selects the hypothesis for the next round's slots.
   - `round-run` is refused until every selected hypothesis has its code committed.
   - This avoids coding hypotheses that later get parked, and code written against a codebase that has since moved on.
9. **The lever coder's contract:**
   - It works in the run worktree, not a Claude-isolated worktree, so the `worktree.baseRef` concern doesn't apply. Coders run one after another, each handling one hypothesis.
   - It reads levers only through `lever()`, with the baseline running the original path, and declares which files it touches.
   - Before committing with `commit-lever <H>`, it must pass `boautoresearch smoke <H>`. The smoke test runs one trial at baseline and one at a random in-range point, at the cheapest rung, charged to the budget.
   - A crash fix that changes what a lever means is a new version.

### Access control
10. **Read-only agents** (both reviewers and the analyst):
    - their `tools` are restricted to Read and Bash;
    - a `PreToolUse` hook matched on their `agent_type` allows Bash only for `boautoresearch` probes and `record`.
11. **The orchestrator reads only probes.** A hook blocks it from reading `.bo-research/artifacts/` or `log.db` directly. It uses the probes or asks the analyst, so a long-lived context doesn't fill up with raw logs.

### When to spend an agent
12. **Agents run only at round boundaries and at registration, never mid-round.** The orchestrator sits idle while `round-run` runs in the background.
    - **Mandatory work,** required through the `next` list: reviews, interplay reviews, code for selected hypotheses, the analyst after every round, expected verdicts, and generation when its trigger fires.
    - **Optional work,** done only through `enqueue`: agent-chosen trials, which are already capped per round.

### Glossary
- Added **Lens**.

### Knock-on for open tickets
- **Enforcement hooks:** add these hooks:
  - `SubagentStop` on each plugin agent type, which calls `boautoresearch check recorded <agent_id>`;
  - a `PreToolUse` Bash allowlist for the read-only agents (`boautoresearch` probes and `record` only);
  - a `PreToolUse` block on the orchestrator reading `.bo-research/artifacts/` or `log.db`.

  `round-run`'s refusal until selected hypotheses have code is a harness refusal, not a hook.
- **Pre-loop grilling script:** collect the number of lenses and the number of proposals per lens. It also needs to support the orchestrator's init duties: proposing the fidelity ladder and choosing lenses from the brief.
- **Final deliverable:** report how accurate the orchestrator's expected verdicts were, which lens each hypothesis came from, and what each lens produced (retained or rejected counts per lens).
