## Resolution

**Prototype:** [`prototype/harness-api`](https://github.com/upadhyan/bo-autoresearch/tree/prototype/harness-api/prototype/harness_api) (commit c443740). It is throwaway and all of its statistics are faked. To replay a scripted session, run `python3 cli.py`. To run the toy project on its own, outside the harness, run `cd toy_project && PYTHONPATH=.. python3 runner.py`.

**Gist:** the harness is a Python package named **`boautoresearch`**. It is bundled inside the plugin and installed into each run's dedicated venv from the plugin's own directory, not from PyPI. It has two surfaces:
- **Runner-side:** six functions that runner scripts and lever code import. That is the whole interface.
- **Agent-side:** a JSON CLI, split into free probes and logged actions. The one deep command is `round-run`, which runs a whole round.

The harness is the **primary enforcer**. Hooks are thin adapters specific to the host, used only for what the harness can't see. Only Claude Code is supported in v1.

### Runner-side surface (`import boautoresearch as bo`)
1. **Six names, and nothing else:**
   - `lever(name)`: the lever's effective value, after masking. This is the only way lever code reads config.
   - `seed()`: the seed the harness assigned.
   - `fidelity()`: this round's rung, e.g. `{"epochs": 3}`.
   - `log(name, value, step=None)`: telemetry. Scalars go on the trial record, and stepped values go to a curve in the artifact folder. It never feeds the sampler, and there is no pruning.
   - `artifact_dir()`: the trial's artifact folder, created on demand.
   - `run(fn)`: the runner's entry point. `fn()` returns the objective, or `(objective, {constraint: value})`.
2. **Running outside the harness** (plain `python runner.py`): `lever()` returns the defaults in a harness-committed `levers.json`. During research those are the baselines. On the distilled branch they are the incumbent's values. The user's code therefore always runs on its own, and the prototype confirmed this.
3. **Generated runner scripts are tiny**, e.g. `bo.run(train_and_eval)`. They name only the objective, and become a protected path once generated.

### Declaring levers
4. **Levers are declared in the hypothesis spec**, passed to `propose`, never in code. Define-by-run in the Optuna style (`trial.suggest_*`) was rejected, because code could quietly change a pre-registered search space. Each lever has:
   - a kind:
     - `float` or `int`, with `low`, `high` and an optional `log`;
     - `categorical`, with `options`;
     - `bool`, which requires a `why_not_graded` field;
   - a `baseline`, which must lie inside the range;
   - a `predicted` direction.

### How trials run
5. **Each trial is a subprocess**, `python runner.py`, run in the run venv inside the worktree. An env var points to the trial's resolved file (levers, seed, fidelity and artifact folder). From outside the trial, the harness:
   - measures wall-clock time, peak memory and the exit code;
   - sends heartbeats;
   - turns exceptions into `trial_failed`.
6. **The objective's direction is set at `init`**, never in the runner.
7. **Trials run in parallel** up to the `workers` setting in the run config, which defaults to 1.

### Agent-side CLI (`boautoresearch <cmd>`, every response in JSON)
8. **Probes** are read-only, cost nothing, and are not logged as decisions:
   - `status`, `summary`, `show <H>`, `verdict <H>`, `trials`, `untested`, `sensitivity <H>`.

   `sensitivity` gives partial-dependence and interaction indices, for telemetry only.
9. **Actions** change state, require `--rationale`, and are logged with their actor:
   - `init`, `propose`, `record`, `register`, `prioritize`, `enqueue`, `round-run`;
   - `park`, `unpark`, `narrow`;
   - `commit-change`, `add-dependency`;
   - `checkpoint`, `stop`, `wrapup`.

   A refused action returns the refusal reason as JSON.
10. **The harness fills round slots, not the orchestrator.** The orchestrator only sets priority, with `prioritize <H> <n>`. At round start, the harness fills slots from the queue by priority, within the dimension cap, placing hypotheses flagged as possibly interacting together. The prototype's `activate` action was dropped.
11. **`round-run` is the deep command.** The orchestrator runs it in the background, and it exits when a harness trigger ends the round. Inside it:
    - calibration and baseline replicates, run automatically as `R0` if they're missing;
    - the eligibility function and study rebuild;
    - replicates, verdict checks and budget refusal;
    - escalation, the end triggers, and regenerating the summaries.

    It returns the round's JSON: the trigger, verdict records, incumbent, and a `next` list of what is blocking.

    The orchestrator never runs a trial by hand. Agent-chosen trials are queued beforehand with `enqueue --config … --expected …`.
12. **`record <kind>` is the single inlet for subagent output.** The kinds are `review`, `interplay`, `expected` and `narrative`. On Claude Code, the `SubagentStop` hook schema-checks each payload before it lands.

### Where enforcement lives
13. **The harness is the primary enforcer**, and its refusals work on any agent host. It refuses:
    - `register` without a reviewer record;
    - `round-run` while blocked (a missing interplay review or expected verdict), or after the run has ended;
    - any trial that would breach the budget reserve or a prohibited predicate;
    - commits that touch protected paths or match forbidden patterns;
    - a dirty worktree or a dirty user tree.
14. **Hooks are thin adapters specific to the host**, used only where the harness can't see:
    - file writes: protected paths, and the worktree during a round;
    - install commands;
    - the agent stopping early;
    - subagent output;
    - session start.

    Each hook calls into the harness for its decision rather than holding logic of its own.

### Scope
15. **v1 supports Claude Code only.** Other agent hosts (Codex, opencode) are out of scope for v1. Because the harness does most of the enforcement, adding them later means writing hook adapters, not a redesign.

### Knock-on for open tickets
- **Enforcement hooks:** hooks are thin adapters that call harness checks (e.g. `boautoresearch check write <path>`, `boautoresearch check stop`) and hold no logic of their own. The ticket should list only what the harness can't see: file writes, installs, stopping, subagent output and session start. Everything else is already a harness refusal.
- **Agent roster and contracts:** the orchestrator skill drives only the CLI listed above. It sets priority but never activates hypotheses, and it runs `round-run` in the background. Subagent outputs land through `record <kind>` (review, interplay, expected, narrative), which fixes the schema per kind. The hypothesis spec format is in item 4.
- **Pre-loop grilling script:** collect the objective's direction and the `workers` count. It generates the tiny runner script (`bo.run(fn)`) and marks it protected.
- **Final deliverable:** the distilled branch ships a `levers.json` holding the incumbent's values, so `lever()` works without the harness. That means the delivered code depends on `boautoresearch`, unless wrap-up inlines the values. Decide which there.
