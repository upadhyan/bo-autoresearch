## Question

What must the run-start grilling session with the user extract before round 1?

Candidates are the objective and its direction, a baseline and noise estimate, budget, constraints, untouchable code, the initial hypothesis set, and **priors on plausible lever ranges that seed round 1**. That last one recovers the early-regret gains 2608.00316 got by having the agent place every trial. Decide what the session writes out and what gates the start of round 1.

## Resolution

**Gist:** pre-loop grilling is the orchestrator skill's first phase, `/boautoresearch:start`. It is split around an automatic **calibration round (R0)**:
1. **Interview part 1** covers everything that needs no data, and ends by writing a `run.yaml` that `init` validates.
2. **R0** runs the smoke test, the fidelity calibration and the baseline replicates.
3. **Interview part 2** uses R0's σ to set δ, fixed for the run, then reviews the generated hypothesis list once, with "go" as the default.

The harness refuses R1 until every precondition holds.

### Session shape
1. **The session is a grilling interview**, with one recommended answer per question, run by the orchestrator skill (`/boautoresearch:start`). The order is interview part 1, then `init`, then R0, then interview part 2, then R1.

### Interview part 1, in order (each topic may depend on the ones before it)
2. **Objective:**
   - the function that produces it, and its direction;
   - where the evaluation code and data splits live, which become protected paths by default;
   - whether the objective is deterministic.

   The skill generates the tiny runner script and runs it once at baseline, outside the harness, to confirm it works.
3. **Research brief:** purpose, what counts as in scope and as a contribution, complexity appetite, and provenance rules.
4. **Directives:** each with a severity (prohibited or discouraged), a reason, and optional predicates and forbidden patterns. Preferences are rewritten as discouraged directives.
5. **Protected paths:** confirm the defaults and take additions.
6. **Fidelity:** the reference fidelity, plus the ladder the orchestrator proposes. The user confirms both.
7. **Budget:**
   - compute time, an optional target and an optional trial-count ceiling;
   - confirming the 5% reserve;
   - `workers` (default 1), k (default 5), and the checkpoint mode.
8. **Seeds and ideas:**
   - up to 5 named seed configs;
   - the user's own hypothesis ideas, with plausible ranges where the user has them;
   - any planned breaking changes.

   Historical results inform rationales only.
9. **Generation:** the lenses the orchestrator proposes from the brief (about 4–6, plus the wildcard) and the number of proposals per lens.

### What the session writes
10. **A `run.yaml` draft**, human-readable, which the user can edit before starting. `boautoresearch init run.yaml` then:
    - validates it;
    - refuses if the user's tree has uncommitted changes;
    - creates the worktree and the venv;
    - logs `run_started` and the first `registry_revised`.

    After that, the log is the source of truth. `run.yaml` becomes a protected record of what was agreed, and changes only at a checkpoint, as a registry revision.

### Calibration round (R0)
11. **R0 runs automatically after `init`**, charged to the budget. It runs the smoke test, then fidelity calibration (ρ, spread, cost per rung), then the k baseline replicates. It produces σ, the chosen rung, or a request to accept an unvalidated proxy.

### Interview part 2
12. **Show R0's results:** σ, the calibration results and chosen rung, and R0's cost against the budget.
13. **Set δ.** The skill suggests δ = 2σ, with an estimate of how many trials a verdict would need at that δ, and warns when δ is impractically small. The user sets δ. δ is **fixed for the run**, because changing it would re-grade every earlier verdict.
14. **The initial hypothesis list.**
    - The lensed generators run, seeing the brief and R0's results.
    - The user's ideas are turned into specs and go through the same review.
    - The skill shows the reviewed list once: title, lens, priority and intent verdict for each hypothesis, plus any pruned or parked ones with their reasons.
    - The user can park, reprioritise or add hypotheses, or just say go.

    This is the last pause before the autonomous loop, unless checkpoint mode is on.

### Dropped
15. **"Priors on lever ranges that seed round 1."** [Warm-start policy](https://github.com/upadhyan/bo-autoresearch/issues/9) already ruled out πBO and range priors. The early-regret gain from 2608.00316 is recovered by the named seed configs, plus the plausible ranges users give for their own ideas.
16. **`init --from <old-run>`** was not included. Add it once repeated runs need it.

### The R1 gate (a harness refusal)
17. **`round-run` for R1 is refused unless all of these hold:**
    - `run_started` is valid, the tree is clean, and the worktree and venv exist;
    - R0 is complete: the smoke test passed, σ is estimated, and calibration is done or the unvalidated proxy was accepted;
    - δ is set;
    - the brief and directive registry exist;
    - at least one hypothesis is registered, its code is committed, and expected verdicts are recorded.

### Glossary
- Added **Calibration round**.

### Knock-on for open tickets
- **Final deliverable:** include what was agreed in `run.yaml` (the brief, directives, δ and budget) and R0's results (σ, calibration and chosen rung), so the report shows the terms the research was run under.
- **Enforcement hooks:** no new hooks. The R1 gate and `init`'s refusals live in the harness.
